# Pollo Móvil — operational collaboration contracts

This is a source-level implementation record, not a declaration that the full operating specification or production readiness is complete. The additive migrations and clients remain local and have not been applied to a remote project in this work.

## Role-separated experiences

- `platform_superadmin` remains a platform identity and is not represented by a restaurant membership. The SaaS platform console and restaurant membership checks are distinct.
- Branch managers and supervisors keep the existing management workspace. They can review task reports, decide meal proposals, inspect source-backed recommendations and edit branch policies.
- Employees receive a dedicated, reduced workspace for their tasks, receipt, coworker notices, own shift/meal status and peer activity reporting. The Edge Function filters members, notices, reports and approved meal slots by the authenticated user; UI separation is not the only access control.
- The web guard validates `is_platform_admin()` before rendering protected content. Authorization lookup failures now fail closed with an explicit retry state instead of treating a network/RPC failure as proof that a platform operator is a tenant user. A worker with no active published shift is shown as off shift, not available.

## Collaborative tasks and evidence

Migration `20261023201359_collaborative_task_receipts.sql` models receipt separately from task completion and provides atomic `open → claimed → resolved` coworker notices. Expired claims can be reclaimed; a peer notification never completes the task. The corresponding event history is append-only and branch scoped.

Receipt-escalation deadlines are now configurable per branch and priority, without a default timeout. The management view counts down to the configured threshold and enables the collaborative-notice action when it is due; when no deadline is configured, a manager can still request the notice manually. A notification never marks receipt or work completion by itself.

The pending local migration `20261024044147_collaborative_notice_automation_and_peer_meals.sql` extends that flow: a `pg_cron` job checks configured receipt deadlines once per minute, atomically opens at most one request per active task, and records a system event with no fabricated human actor. It notifies only coworkers currently available on a published shift, excluding occupied, meal/rest/off-shift, absent, on-break, or task-busy members. Reservation expiry reopens the request; a configured branch-level escalation delay notifies managers if it remains unclaimed. An unset delay does not invent an escalation time. Manual manager requests remain supported, and confirmation by the assigned employee cancels any active notice without completing the task. These changes are source-only until the migration is explicitly applied and runtime behavior is verified.

Migration `20261024010441_operational_collaboration_meals_and_reporting.sql` adds explicit evidence policies (`none`, `optional`, `required`, `independent_review`), peer reports, immutable recorded time, declared completion time, and separate reviewer decisions. Required evidence is uploaded to private Storage and the manager obtains only a short-lived signed read URL. A report requiring independent review cannot be accepted by its own reporter. Reported activity remains pending until an authorized review accepts it.

The Flutter employee experience and Next.js employee workspace expose receipt confirmation, `Voy a avisarle`, `Ya le avisé`, `No pude localizarlo`, and peer reporting. Realtime updates refresh these views; stale push notifications reconcile against the current request state when opened.

## Availability and meal policy

Branch meal duration and collaborative-notice reservation expiry are nullable settings; no branch-specific duration or five-minute default is invented. Workers can explicitly change between available and occupied; management may record rest or off-shift status. Current state is a branch-scoped projection, while each actual transition is retained in an append-only event ledger; repeated writes of the same state do not fabricate another transition. Meals require active published shift, configured duration, no unfinished in-progress task/part, and a separately confirmed return. Elapsed scheduled time never makes an employee available automatically. The pending migration adds self/peer/manager origin and optional declared start/return timestamps to meal sessions; database recording timestamps remain authoritative and meal events separately retain employee, actor, recorded time, declared time (null when omitted), and origin. Web `datetime-local` values are interpreted in the branch timezone, while mobile sends an absolute timestamp. A currently available coworker may record a peer meal start or confirmed return for an active-shift coworker without a personal device; server-side checks revalidate both branch membership and current availability. RLS permits meal Realtime reads only to the employee, managers, or an available same-branch coworker while the target is on shift. Historical sessions are not backfilled with invented declared times.

Managers can request a Timefold meal proposal for an explicit local shift date. The solver uses published shifts, shift breaks, approved absences, current operational status (for the current local date), existing/active meals, and in-progress tasks/parts. The solver rejects overlapping meals, which conservatively leaves all but one eligible worker unavailable at a time, and prefers each worker's shift midpoint when other constraints allow. Where a minimum area coverage policy is configured, every meal start is blocked if removing that worker would reduce qualified scheduled headcount below the configured minimum at any point in the meal. The response is revalidated before it is stored with `planner = timefold`; an unavailable or infeasible Timefold service does not silently create a local proposal.

The current source model does not contain approved task time windows or a trusted demand feed. The meal solver therefore cannot optimize against task overlap, real-time customer flow, or demand forecasts. Its conservative one-at-a-time schedule is a feasible proposal, not an optimized staffing forecast. Manager approval is required, and approval does not start meals or change current operational state. Approved slots are normalized into employee-scoped rows, so an employee sees only their own approved time in web and Flutter/Realtime.

`restaurant_positions.area_id` is a nullable same-branch relationship configured explicitly by a manager. Coverage analysis counts only published, qualified headcount with exactly one mapped area; it excludes approved absences and, for today's date only, active meal/rest/off-shift state. Results are labeled as scheduled qualification, not live physical location. Coverage findings have source period/data and human decisions, and upserts are deduplicated per area/interval.

Managers can also analyze a bounded period of persisted task-assignment events and inspections. Workload findings expose only aggregate event counts and task-estimated minutes (not employee-level performance); divided task parts are excluded because their assignment history is not currently stored in the same append-only ledger. Day-overdue counts use the task's scheduled local date and do not invent an intraday deadline. Inspection findings come from persisted `needs_attention_count`. Source inputs and the exact period are stored, confidence remains unset, and the manager must approve or reject. The analysis does not use POS, demand estimates, phone connectivity, or a fabricated measurement of labor time.

## Existing and remaining boundaries

The existing task assignment solver continues to use Timefold when configured and an explicit TypeScript fallback otherwise; the new meal solver has no such fallback. Existing Android/iOS/web flows, access rules, RLS, migrations, and artifacts still require the final validation phase. Additional rest scheduling with separately configurable duration/frequency, trusted demand analytics, task-window scheduling, independent visual QA of evidence, and final multi-client acceptance remain unfinished until verified. The current history report can detect overdue-by-day, not recurrent within-day lateness, because the source schema has no task due time.

No branch, employee, official schedule, or Madero operating data is created by these changes. GPS remains optional and event-only for clock-in/out. No remote database, Vercel project, repository, or deployment is modified.
